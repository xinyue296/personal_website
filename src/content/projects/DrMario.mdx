*Computer Organization, University of Toronto, Fall 2024. Solo project. The code stays private because it is coursework, so this page describes the game instead.*

I remade Dr. Mario in MIPS assembly, running on a 64 by 64 bitmap display with keyboard input. There is no game engine, no standard library, and no compiler to lean on. Every pixel is a value written to a memory address, and every function call is a stack frame I set up and tore down myself.

## Playing it

![The start menu, reading n-Start and q-Quit in hand-drawn pixel lettering on a blue background](/assets/projects/drmario/menu.png)

The game opens on a start menu. Press **n** to start and **q** to quit. Capsules drop from the neck of the pill bottle, and you steer them with **a** and **d**, rotate with **w**, and push them down with **s**. Line up four of the same colour in a row or column to clear them, and anything left unsupported falls into place. Clear all four viruses to win. Block the neck of the bottle and it is game over, with an option to retry.

![The full game board, with the pill bottle in the middle, the three virus sprites down the left side, the capsule queue along the shelf and pixel-art Dr. Mario filling the right panel](/assets/projects/drmario/cleared.png)

Everything on that screen is drawn by hand. The bottle, the viruses, the queue along the shelf, and the doctor on the right are all rectangles and lines written to memory addresses.

## Beyond the required milestones

On top of the core game I added eight features.

- Gravity, so capsules fall on their own.
- Gravity that speeds up the longer you play.
- Game over with a retry option.
- Pause and resume with **p**, with a pause sign on screen.
- A side panel previewing the next capsule.
- A preview queue of the next five capsules.
- Pixel-art Dr. Mario and viruses on the side panels, drawn pixel by pixel.
- Hold a capsule with **k** and bring it back later.

![The same board with a red capsule half parked in the hold slot in the top left corner](/assets/projects/drmario/hold.png)

Paused one move before a four-in-a-column clear, and a capsule parked in the hold slot.

That sprite is not an image file. It is 82 draw calls in assembly, each one a line or a rectangle at coordinates I worked out on grid paper first, in colours defined by hand at the top of the program.

## How I built it

Before writing any assembly, I sketched the whole screen on grid paper, with the bottle's exact dimensions, where each panel sits, and the four rotation states of a capsule. In assembly, every coordinate turns into an address calculation, so having the layout on paper first gave me exact numbers to work from.

![Grid paper sketch of the screen layout, with the bottle measured out in squares and the four rotation states of a capsule drawn beside it](/assets/projects/drmario/plan.jpg)

The game runs as a frame loop. Each frame reads the keyboard, applies the move, advances a gravity counter, checks for matches, and redraws the board. The board lives in memory as a grid, so collision checks, clears, and the cascading drops are all loops over that grid.

## What I took from it

Calling conventions, the stack, and memory-mapped input and output stopped being abstract once I had to manage every one of them myself. It is also the project that made me curious about how software meets hardware, which is why I am taking systems courses this year. And it was genuinely fun.
